# Taskflow

Automated task triage and implementation from project management tools like ClickUp.

Taskflow is a Claude Code plugin that pulls tasks from your project management tool, classifies them, creates implementation plans, groups them into smart batches, and then implements each batch — complete with worktrees, tests, and PRs.

## Installation

```bash
claude plugins marketplace add github:rentorious/taskflow
claude plugins install taskflow@taskflow
```

After installing, restart Claude Code for the skills to become available.

## Quick Start

1. **Setup** — Run `/taskflow:setup` to generate `.claude/taskflow-config.json` for your project. The wizard auto-detects your codebase structure and walks you through connecting your project management tool.

2. **Triage** — Run `/taskflow:triage` to pull your assigned to-do tasks, classify them, create per-task implementation plans, and group them into batches.

3. **Report** — Run `/taskflow:report` at any point to open the report in your browser: what is waiting on you, what is ready to claim, what is in flight and what is blocked. It updates itself while implement sessions work.

4. **Implement** — Run `/taskflow:implement` to execute the next batch: creates a worktree, implements changes, runs checks, updates task statuses, and opens a PR.

5. **Clean** — Run `/taskflow:clean` when a cycle is done. It stops the report server and archives the index, batches, plans and attachments to `<output_dir>/archive/<cycle-date>/`, so the next triage starts from a blank slate. `--purge` deletes everything instead.

## Skills

| Skill | Command | Purpose |
|-------|---------|---------|
| Setup | `/taskflow:setup` | Interactive wizard to generate project config |
| Triage | `/taskflow:triage` | Fetch, classify, plan, and batch tasks |
| Implement | `/taskflow:implement` | Execute a batch: implement, verify, PR |
| Report | `/taskflow:report` | Live report grouped by what happens next, with an inbox of things that wait on you |
| Clean | `/taskflow:clean` | Archive (or `--purge`) the local state to start a fresh cycle |

## The report

`/taskflow:report` starts a small local server (Node 18.17+, no dependencies, `127.0.0.1` only) and prints its URL.

- **A queue grouped by what happens next.** Needs you, ready to start, in flight, pull request open, blocked, shipped and stale, not batched. "Ready to start" is exactly what `/taskflow:implement` would claim, in the order it would claim it; "Blocked" names the batches it waits on.
- **An inbox.** Questions for the client, provider writes that failed and must be pasted by hand, fixes to verify and close, and broken pipeline state such as a stale lock. Copy the text, tick the item off, and it moves to "waiting" or out of the way. Ticks live in `report-inbox.<slug>.json`; the report never writes pipeline state.
- **The plan next to the queue.** Each batch opens with its command, branch, dependencies, time estimates, the per-task plans and screenshots.
- **Pull request state and leftover worktrees**, when `gh` and `git` are available. Without them the report still works.
- **Archives.** Every cycle archived by `/taskflow:clean` stays selectable, read-only.
- **A snapshot.** `/taskflow:report --snapshot` writes the whole report as one HTML file that opens without a server.

## Config Reference

The config file lives at `.claude/taskflow-config.json` in your project. It's generated by `/taskflow:setup` and consumed by the other skills.

| Field | Description |
|-------|-------------|
| `version` | Schema version (currently `1`) |
| `provider` | Project management tool (`"clickup"`) |
| `project_name` | Used for worktree naming |
| `clickup` | Provider-specific config (workspace, lists) |
| `areas` | Classification areas with paths and verification commands |
| `extra_areas` | Non-code classification areas (e.g., `"sendgrid"`, `"manual"`) |
| `branch_conventions` | Branch prefix mapping by task type |
| `output_dir` | Where state/plan files are written |
| `base_branch` | Branch to create worktrees from |
| `build_before_implement` | Commands to run in worktree before implementation |
| `install_command` | Dependency installation command |
| `full_lint` | Full-repo lint command |
| `full_typecheck` | Full-repo typecheck command |
| `provider_comments` | **Default `false`.** Post developer-voice comments back to the provider. See below |

### Provider comments (off by default)

Taskflow used to write a developer-voice comment on every task — a clarification question during triage, a "here's what I changed + PR link" note during implement. That is now **disabled by default**, because comment volume is permanent provider-side storage and counts against free-plan quotas.

With `provider_comments` absent or `false`:

- No comments are posted, ever.
- Clarification questions for low-confidence tasks are still drafted — they land in the task's plan file under `## Open Question` and in the triage summary under **Low Confidence Tasks**, ready to paste manually.
- PR URLs still land in the batch file and the implement terminal summary; the PR body links every task.
- Status transitions (`to do` → `in progress` → `code review`), description enrichment, and duplicate task links are unaffected — those overwrite rather than accumulate.

To opt back in, set it in `.claude/taskflow-config.json`:

```json
"provider_comments": true
```

## Development

The plugin has no build step and no dependencies. The report's tests run on plain Node:

```bash
node --test "test/*.test.mjs"
```

To look at the report without a real project, write a synthetic cycle to disk and point a second server at it:

```bash
node test/fixtures/materialize.mjs kitchen-sink /tmp/taskflow-kitchen-sink
node scripts/report-server.mjs --dir /tmp/taskflow-kitchen-sink --port 3848 --no-pidfile
```

Fixtures are generated by code (`test/fixtures/specs.mjs`) and are entirely invented. This repository is public: never commit real task titles, provider ids, client names or pull request URLs.
